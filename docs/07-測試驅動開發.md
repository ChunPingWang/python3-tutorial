# 第 7 章：測試驅動開發 —— 從 `assert` 到 pytest

> 🎬 **情境**
> 阿宏的系統已經有 12 個函式，你累積了 40 幾個 `assert`。今天他說：「會員折扣改成滿 200 才有。」
>
> 你改完，把那 40 個 `assert` 從頭執行一遍——第 7 個就掛了。你修好第 7 個，再從頭跑一遍——第 23 個掛了。
> 跑到第 23 個的時候，前面 22 個又被你改壞了嗎？你不知道，因為 `assert` 一失敗，**後面的就不會執行了**。

---

## 7.1 😩 土法煉鋼：一整片 `assert` 的極限

```python
assert price_of("珍珠奶茶", "大杯") == 65
assert price_of("珍珠奶茶", "中杯") == 55        # ← 這裡失敗
assert price_of("冬瓜檸檬", "大杯") == 45        # ← 以下全部不會執行
assert price_of("冬瓜檸檬", "中杯") == 40
# ... 還有 37 個
```

`assert` 到了這個規模，有四個問題：

| 問題 | 具體狀況 |
| --- | --- |
| **失敗就中斷** | 一次只能知道一個錯，修 40 個要跑 40 次 |
| **沒有報表** | 不知道「總共幾個、過了幾個、哪些過了」 |
| **不知道為什麼錯** | `AssertionError` 只說「不成立」，沒說「預期 55、實際 60」 |
| **沒有組織** | 40 個測試混在一起，不知道哪些是測折扣、哪些是測菜單 |

你需要的東西很明確：**跑完全部、告訴我哪些過哪些沒過、失敗時告訴我預期和實際是什麼。**

這就是測試框架存在的理由。

---

## 7.2 TDD 的完整循環

在介紹工具之前，先把方法講清楚。TDD 只有三個步驟，循環進行：

```
        ┌─────────────────┐
        │  🔴 紅：寫一個   │
        │  會失敗的測試    │
        └────────┬────────┘
                 ↓
        ┌─────────────────┐
        │  🟢 綠：寫剛好   │
        │  夠通過的程式    │
        └────────┬────────┘
                 ↓
        ┌─────────────────┐
        │  🔵 重構：在測試 │
        │  保護下整理程式  │
        └────────┬────────┘
                 ↓
            回到 🔴
```

### 每一步的紀律

**🔴 紅燈階段**

- 一次只寫**一個**測試
- 執行它，**確認它是因為「功能還沒做」而失敗**，不是因為測試本身有 typo
- 看清楚錯誤訊息長什麼樣（之後你會靠它 debug）

**🟢 綠燈階段**

- 寫**剛好夠**通過的程式，不要多寫
- 「不要多寫」是認真的：如果測試只要求 `price_of("珍珠奶茶","大杯") == 65`，
  你寫 `return 65` 是**完全合法**的第一步。聽起來很蠢，但它逼你用下一個測試說清楚真正的規則。
  （這個技巧叫 *fake it till you make it*。）

**🔵 重構階段**

- **不能新增功能**，只能改善結構：改名、抽函式、去重複
- 每改一小步就跑一次測試
- 測試一旦變紅，立刻退回上一步

### 為什麼順序不能顛倒？

**先寫程式再補測試**，你的測試會被你的實作綁架 ——
你會不自覺地只測「你寫得出來的東西」，而不是「使用者真正需要的東西」。

真實例子：

```python
# 先實作的人寫出這個函式
def 計算折扣(金額, 折數):
    return 金額 * 折數

# 再補測試,他會測什麼?
assert 計算折扣(100, 0.9) == 90.0        # 只驗證了他寫的那行
```

```python
# 先寫測試的人會先問:「使用者會怎麼用?」
assert 計算折扣(100, 0.9) == 90          # 要整數還是小數?
assert 計算折扣(65, 0.9) == 59           # 58.5 怎麼辦?
assert 計算折扣(100, 0) == 0             # 折數 0 合理嗎?
assert 計算折扣(100, 1.5) == ???         # 折數大於 1 呢?應該報錯吧?
```

**第二組測試會逼出一個好上許多的函式。**

## 7.4 `doctest`：讓說明文件變成測試

還記得第 6 章的 docstring 嗎？在裡面寫互動式範例，它就變成可執行的測試：

```python
def round_half_up(value: float) -> int:
    """台灣習慣的四捨五入(逢五進一)。

    >>> round_half_up(58.5)
    59
    >>> round_half_up(2.5)
    3
    >>> round_half_up(204.75)
    205
    """
    from decimal import Decimal, ROUND_HALF_UP
    return int(Decimal(str(value)).quantize(Decimal("1"), rounding=ROUND_HALF_UP))
```

執行：

```bash
python3 -m doctest 你的檔案.py -v
```

在 Jupyter 裡：

```python
import doctest
doctest.testmod(verbose=False)
```

**doctest 的殺手級價值：文件和程式不會再脫節。**
你改了行為卻忘了改文件？doctest 會失敗，逼你更新。

⚠️ **限制**：doctest 比對的是**輸出的字串**，一字不差。所以：

- 浮點數 `0.30000000000000004` 這種東西不適合寫進 doctest
- 字典在舊版 Python 順序不保證（3.7+ 已保證插入順序，還好）
- 例外訊息包含路徑時會失敗

**準則：doctest 用來寫「給人看的漂亮範例」，複雜的邊界測試交給 pytest。**

## 7.5 `unittest`：標準庫的測試框架

```python
import unittest

class TestPricing(unittest.TestCase):

    def setUp(self):
        """每個測試方法執行前都會跑一次,用來準備資料。"""
        self.menu = {"珍珠奶茶": {"中杯": 55, "大杯": 65}}

    def test_一般價格(self):
        self.assertEqual(price_of("珍珠奶茶", "大杯"), 65)

    def test_會員折扣(self):
        self.assertEqual(price_of("珍珠奶茶", "大杯", is_member=True), 59)

    def test_不存在的品項會拋出_KeyError(self):
        with self.assertRaises(KeyError):
            price_of("綠茶", "大杯")
```

執行：

```bash
python3 -m unittest -v          # 終端機
```

```python
unittest.main(argv=[""], exit=False)    # Jupyter 裡
```

輸出：

```
test_一般價格 ... ok
test_會員折扣 ... FAIL
test_不存在的品項會拋出_KeyError ... ok

FAIL: test_會員折扣
AssertionError: 60 != 59      ← 告訴你預期和實際!
Ran 3 tests in 0.001s
FAILED (failures=1)
```

**三個 `assert` 做不到的事，它都做到了**：全部跑完、有統計、有預期/實際對照。

常用斷言方法：

| 方法 | 意思 |
| --- | --- |
| `assertEqual(a, b)` | a == b |
| `assertTrue(x)` / `assertFalse(x)` | 真假 |
| `assertIn(a, b)` | a in b |
| `assertIsNone(x)` | x is None |
| `assertRaises(錯誤型別)` | **應該要拋出例外** |
| `assertAlmostEqual(a, b)` | 浮點數比較 |

⚠️ unittest 的缺點是**囉嗦**：要建類別、要繼承、方法名要以 `test_` 開頭、斷言要背一堆方法名。
所以有了 pytest。

## 7.6 `pytest`：業界標準

```bash
pip install pytest
```

同樣的測試，pytest 版本：

```python
# tests/test_pricing.py
import pytest
from drinkshop.pricing import price_of

def test_一般價格():
    assert price_of("珍珠奶茶", "大杯") == 65

def test_會員折扣():
    assert price_of("珍珠奶茶", "大杯", is_member=True) == 59

def test_不存在的品項會拋出_KeyError():
    with pytest.raises(KeyError):
        price_of("綠茶", "大杯")
```

**沒有類別、沒有繼承、就用原生的 `assert`。** 執行：

```bash
pytest -v
```

失敗時 pytest 會自動幫你拆解 `assert`：

```
E       assert 60 == 59
E        +  where 60 = price_of('珍珠奶茶', '大杯', is_member=True)
```

它連「這個 60 是從哪個呼叫來的」都告訴你了。這叫 *assertion rewriting*，是 pytest 最受歡迎的功能。

### pytest 的三個必學功能

**1️⃣ 參數化：一個測試涵蓋很多案例**

```python
@pytest.mark.parametrize("name,size,expected", [
    ("珍珠奶茶", "中杯", 55),
    ("珍珠奶茶", "大杯", 65),
    ("冬瓜檸檬", "中杯", 40),
    ("冬瓜檸檬", "大杯", 45),
])
def test_菜單價格(name, size, expected):
    assert price_of(name, size) == expected
```

這會產生 **4 個獨立的測試**，任何一個失敗都不影響其他三個，而且報表會告訴你是哪一組失敗。

**2️⃣ fixture：共用的準備工作**

```python
@pytest.fixture
def 今日訂單():
    return [65, 45, 120]

def test_總營收(今日訂單):        # 參數名對上 fixture 名,pytest 自動注入
    assert sum(今日訂單) == 230
```

**3️⃣ `tmp_path`：測試檔案讀寫用的暫存目錄（跨平台）**

```python
def test_存檔(tmp_path):
    檔案 = tmp_path / "報表.csv"      # 自動建立、測試結束自動刪除
    存檔(檔案, "內容")
    assert 檔案.read_text(encoding="utf-8") == "內容"
```

⚠️ **永遠不要在測試裡寫死路徑**（如 `/tmp/test.csv` 或 `C:\temp\test.csv`），那在別的作業系統上會失敗。
**`tmp_path` 是跨平台的正確答案。** 第 9 章會深入。

### 常用指令

```bash
pytest                      # 跑全部
pytest -v                   # 顯示每個測試的名字
pytest -x                   # 第一個失敗就停
pytest -k "會員"            # 只跑名字含「會員」的測試
pytest tests/test_pricing.py::test_會員折扣    # 只跑指定的一個
pytest -q                   # 安靜模式
pytest --lf                 # 只重跑上次失敗的(last failed)← 超好用
```

## 7.7 怎麼寫出好測試

### AAA 結構：Arrange / Act / Assert

```python
def test_會員買大杯珍奶有九折():
    # Arrange 準備
    name, size = "珍珠奶茶", "大杯"

    # Act 執行
    實際 = price_of(name, size, is_member=True)

    # Assert 驗證
    assert 實際 == 59
```

三段式讓測試好讀。你一眼就看得出「給了什麼、做了什麼、期待什麼」。

### 測試名稱要說「行為」，不是「函式名」

```python
def test_price_of():              # ✖ 看不出在測什麼
def test_會員買大杯有九折():        # ✔ 這根本就是一句規格
def test_品項不存在時拋出KeyError(): # ✔
```

**好的測試名稱集合起來，就是一份永遠不會過期的規格書。**

### 一個測試只驗證一件事

```python
# ✖ 一個測試塞五件事,失敗時不知道是哪件壞了
def test_價格():
    assert price_of("珍珠奶茶", "大杯") == 65
    assert price_of("珍珠奶茶", "中杯") == 55
    assert price_of("冬瓜檸檬", "大杯") == 45

# ✔ 用參數化拆開
@pytest.mark.parametrize(...)
```

### 一定要測邊界

**bug 最愛藏在邊界。** 每個條件式都問自己：

| 條件 | 要測的值 |
| --- | --- |
| `金額 >= 200` 打折 | 199、**200**、201 |
| 清單處理 | **空清單**、一個元素、很多元素 |
| 字串處理 | **空字串**、只有空白、超長字串 |
| 除法 | **除數為 0** |
| 數量 | 0、負數、非整數 |

```python
def test_空訂單的營收是零():
    assert 總營收([]) == 0        # ← 這種測試最容易被忘記,也最容易出事
```

### 什麼**不該**測

別被「測試覆蓋率要 100%」綁架。以下不值得測：

- **第三方套件的行為**（`pandas` 的 `sum` 對不對不是你的責任）
- **Python 內建功能**（不用測 `len()` 會不會算錯）
- **純粹的資料定義**（`MENU = {...}` 沒有邏輯可測）
- **只是把參數轉手傳給別人的一行函式**

**測「你自己寫的邏輯」和「會出錯的地方」。**

### 測試要快

慢的測試沒人會跑，沒人跑的測試等於沒有。

- 單元測試應該在**幾毫秒**內完成
- 不要在單元測試裡連資料庫、打 API、`sleep()`
- 這些留給數量少得多的「整合測試」

## 7.8 🔴🟢🔵 完整實作一輪

阿宏的新需求：**「滿 200 才給會員折扣。」**

### 🔴 第一圈：紅

```python
def test_未滿200的會員不打折():
    assert 結帳(金額=150, 是會員=True) == 150
```

```
NameError: name '結帳' is not defined
```

### 🟢 第一圈：綠（寫剛好夠的）

```python
def 結帳(金額, 是會員):
    return 金額
```

通過了。**是的，這個實作完全沒用到「是會員」——這很正常。**
現在的測試只要求這件事，下一個測試會逼我寫出真正的邏輯。

### 🔴 第二圈：紅

```python
def test_滿200的會員打九折():
    assert 結帳(金額=200, 是會員=True) == 180
```

```
assert 200 == 180
```

### 🟢 第二圈：綠

```python
def 結帳(金額, 是會員):
    if 是會員 and 金額 >= 200:
        return round_half_up(金額 * 0.9)
    return 金額
```

### 🔴 第三圈：邊界

```python
def test_剛好199不打折():
    assert 結帳(金額=199, 是會員=True) == 199     # 綠,已經對了

def test_非會員滿200也不打折():
    assert 結帳(金額=200, 是會員=False) == 200    # 綠
```

兩個都直接綠。**這也是有價值的** —— 它們變成了「規則的護欄」，
以後有人改壞這個行為，它們會立刻叫出來。

### 🔵 重構

```python
MEMBER_THRESHOLD = 200      # 把魔術數字命名
MEMBER_RATE = 0.9

def 結帳(金額: int, 是會員: bool) -> int:
    """回傳應收金額;會員消費滿 MEMBER_THRESHOLD 元享 9 折。"""
    if 是會員 and 金額 >= MEMBER_THRESHOLD:
        return round_half_up(金額 * MEMBER_RATE)
    return 金額
```

跑測試 → 4 個全綠 → **重構成功**。

隔天阿宏說「門檻改成 300」，你只要改一個常數，而且立刻知道有沒有改壞。
