# 第 14 章：綜合專案 —— 用 TDD 做出營運儀表板

> 🎬 **情境（最終回）**
> 阿宏：「下週要跟投資人開會。我要一份月報：每天的營收、熱銷前三名、滯銷品、
> 會員佔比、客單價。要能從我 POS 匯出的 CSV 直接讀，而且小美用 Windows 也要能跑。」
>
> 這一次，你不是要學新語法。**你要把前 13 章的東西組合起來，交付一個真正的東西。**

---

## 14.1 這一章的做法

我們不會「先想好架構再寫程式」，而是**完全按照 TDD 的節奏走**：

```
每一個功能:
  🔴 寫一個會失敗的測試(同時釐清需求)
  🟢 寫剛好夠通過的程式
  🔵 重構
```

成品就是 [`examples/`](../examples/) 裡的 `drinkshop` 套件。
**建議你先自己跟著做一遍，卡住再去看答案。**

---

## 14.2 第一步：把需求變成測試清單

**不要先開檔案，先開一張清單。** 把阿宏的話翻譯成可驗證的句子：

```
□ 能從菜單查出價格
□ 會員滿 200 打 9 折,未滿不打
□ 員工價 40 一律優先
□ 一筆訂單知道自己的小計和應付金額
□ 能把多筆訂單加總結帳
□ 能算出:總營收、總杯數、客單價(平均與中位數)、會員佔比
□ 能算出熱銷前三名
□ 能算出完全沒賣的滯銷品
□ 能把訂單存成 CSV,也能讀回來(而且讀回來要一模一樣)
□ 能讀一整個資料夾的日報,產生月報
□ 沒有訂單時不能崩潰
□ 品項不存在時要明確報錯,不能默默算 0
□ Windows / macOS / Linux 都要能跑
```

> 🔍 **這張清單就是你的驗收標準，也是你的測試檔大綱。**
> 每完成一項就劃掉一項。你永遠知道還剩多少，而且永遠有一個可執行的版本。
>
> 對比「先寫 800 行再執行」的做法：你會在最後一刻同時面對 30 個 bug，
> 而且不知道是哪一個造成的。

### 決定檔案結構（讓測試的 `import` 來決定）

```python
from drinkshop.pricing import line_price      # 計價
from drinkshop.orders import Order, checkout  # 訂單
from drinkshop.report import daily_report     # 報表
from drinkshop.storage import save_orders     # 檔案
```

寫出這四行，結構就定了。

## 14.3 🔴🟢🔵 第一輪：計價

### 🔴 紅

```python
# tests/test_pricing.py
from drinkshop.pricing import unit_price

def test_查得到菜單上的價格():
    assert unit_price("珍珠奶茶", "大杯") == 65
```

```
ModuleNotFoundError: No module named 'drinkshop'
```

**這也是紅燈**，而且它在告訴你：該建立套件了。

### 🟢 綠

```python
# drinkshop/menu.py
MENU = {"珍珠奶茶": {"中杯": 55, "大杯": 65}}

# drinkshop/pricing.py
from drinkshop.menu import MENU

def unit_price(name, size):
    return MENU[name][size]
```

```python
# drinkshop/__init__.py   （空的也可以）
```

```bash
pytest -v
# test_查得到菜單上的價格 PASSED
```

### 🔴 下一個：品項不存在時怎麼辦？

**這是 TDD 逼你思考的地方。** 三個選項：

| 選項 | 後果 |
| --- | --- |
| 回傳 0 | 阿宏少收錢三個月才發現 ❌ |
| 回傳 None | 呼叫方忘記檢查 → 後面某處 `TypeError` ❌ |
| **拋出例外** | 立刻爆、立刻知道 ✔ |

```python
def test_品項不存在要拋出MenuItemNotFound():
    with pytest.raises(MenuItemNotFound):
        unit_price("綠茶", "大杯")
```

### 🟢 綠

```python
# drinkshop/errors.py
class DrinkShopError(Exception): ...
class MenuItemNotFound(DrinkShopError): ...

# drinkshop/pricing.py
def unit_price(name, size):
    try:
        return MENU[name][size]
    except KeyError as exc:
        raise MenuItemNotFound(f"菜單上沒有「{name} / {size}」") from exc
```

### 🔴 會員折扣：邊界三兄弟

```python
def test_未達門檻不打折():   assert apply_member_discount(199) == 199
def test_剛好達到就打折():   assert apply_member_discount(200) == 180
def test_超過門檻打折():     assert apply_member_discount(500) == 450
```

⚠️ 注意 `200 * 0.9 = 180.0`，而 `65 * 0.9 = 58.5`。
**58.5 要變 58 還是 59？** 這就是第 2 章的銀行家捨入問題 —— 用 `round_half_up`。

### 🔵 重構

把魔術數字變成常數：

```python
MEMBER_RATE = 0.9
MEMBER_THRESHOLD = 200
STAFF_PRICE = 40
TAX_RATE = 0.05
```

跑測試 → 全綠 → 重構成功。

> 🔍 **注意重構的定義：改善結構，不改變行為。**
> 「把 `200` 改成 `MEMBER_THRESHOLD`」是重構；
> 「把門檻從 200 改成 300」不是重構，那是改需求，需要先改測試。

## 14.4 🔴🟢🔵 第二輪：訂單

### 🔴 紅：測試決定了 Order 長什麼樣

```python
def test_訂單會自己算應付金額():
    assert Order("珍珠奶茶", "大杯", 2).total == 130

def test_內容相同的兩筆訂單相等():
    assert Order("珍珠奶茶", "大杯", 2) == Order("珍珠奶茶", "大杯", 2)
```

第二個測試就是在要求 `__eq__` —— 也就是在要求你用 `@dataclass`。

### 🟢 綠

```python
@dataclass
class Order:
    item: str
    size: str = "中杯"
    quantity: int = 1
    is_member: bool = False
    toppings: list[str] = field(default_factory=list)   # ⚠️ 不能寫 = []

    @property
    def total(self) -> int:
        return line_price(self.item, self.size, self.quantity,
                          is_member=self.is_member)
```

### 🔴 別忘了可變預設值的回歸測試

```python
def test_每筆訂單有自己的加料清單():
    a, b = Order("珍珠奶茶"), Order("紅茶拿鐵")
    a.toppings.append("珍珠")
    assert b.toppings == []
```

這個測試看起來很蠢，但**它防的是第 6 章那個惡名昭彰的陷阱**。
每個你踩過的坑，都值得留一個測試。

### 🔴 使用者輸入：把「決定」和「互動」分開

```python
def test_不合法的輸入一律拋出InvalidInput():
    for raw in ["兩杯", "", "0", "-1", "51", "3.5"]:
        with pytest.raises(InvalidInput):
            parse_quantity(raw)
```

⚠️ **注意 `parse_quantity` 不含 `input()`。**
`input()` 沒辦法測試（測試會卡住等輸入），所以它留在 `cli.py`。

```python
# ✔ 可測試:只負責「判斷」
def parse_quantity(raw: str) -> int: ...

# ✖ 不可測試:混了「互動」
def ask_quantity():
    return int(input("請輸入數量:"))
```

**這是整個專案最重要的設計決策。**

## 14.5 🔴🟢🔵 第三輪：報表

### 🔴 先寫最容易被忘記的測試：空的

```python
def test_空訂單的營收是零():
    assert revenue([]) == 0

def test_空訂單的平均是零而不是除以零錯誤():
    assert average_ticket([]) == 0
```

**打烊時如果一筆訂單都沒有，日報表不該掛掉。**
這種「零筆資料」的情況，在真實世界絕對會發生（週一公休、颱風天）。

### 🔴 為什麼要中位數

```python
def test_中位數不會被團購拉走():
    orders = [
        Order("四季春茶", "中杯"),         # 30
        Order("珍珠奶茶", "中杯"),         # 55
        Order("珍珠奶茶", "大杯", 20),     # 1300 團購
    ]
    assert average_ticket(orders) == 462   # 被拉高了
    assert median_ticket(orders) == 55     # 比較真實
```

**這個測試同時是程式碼和文件**：它解釋了「為什麼我們要算兩種客單價」。

### 🔴 日期不能依賴「今天」

```python
REPORT_DAY = date(2026, 9, 20)      # 寫死的常數

def test_日報表包含關鍵數字():
    text = daily_report(sample_orders(), on=REPORT_DAY)
    assert "320" in text
    assert "週日" in text
```

⚠️ 如果 `daily_report` 內部用 `date.today()`，這個測試**今天會過、下週會掛**。
**把「今天」變成參數 `on`。**

### 🔴 星期名稱不能用 `strftime("%A")`

```python
def test_日報表的星期名稱不受系統語系影響():
    assert "週一" in daily_report([], on=date(2026, 9, 21))
```

`strftime("%A")` 在你的 Mac 上是 `Sunday`，在阿宏設定過語系的 Linux 上可能是 `週日`。
**自己做對照表**，輸出才在三個平台一致。

### 🔵 重構：測試「內容包含什麼」，不要整份字串比對

```python
# ✖ 脆弱:改一個空格就壞
assert daily_report(...) == "==========\n  阿宏手搖飲...\n=========="

# ✔ 穩健:測真正在意的東西
assert "320" in text
assert "珍珠奶茶" in text
```

> 🔍 **測試要測「行為」，不要測「長相」。**
> 排版是會改的，數字對不對才是重點。

## 14.6 🔴🟢🔵 第四輪：存檔（跨平台的考驗）

### 🔴 最重要的一個測試：round-trip

```python
def test_存檔再讀回來要一模一樣():
    with tempfile.TemporaryDirectory() as tmp:
        path = Path(tmp) / "訂單.csv"
        save_orders(SAMPLE, path)
        loaded = load_orders(path)

    assert loaded == SAMPLE          # 靠 dataclass 的 __eq__，一行比完
```

**「存進去再讀出來要一模一樣」** 是所有 I/O 程式的黃金測試。
它一口氣驗證了寫入格式、讀取解析、型別轉換、編碼，全部。

### 🔴 這個測試會抓到什麼？

第一次寫完你會失敗，因為：

```
AssertionError: Order(quantity='2') != Order(quantity=2)
```

**CSV 讀進來全部是字串。** 你忘了轉型。這正是我們要這個測試的原因。

```python
quantity=int(row["數量"]),                    # ← 補上
ordered_on=date.fromisoformat(row["日期"]),   # ← 日期也要
```

### 🔴 三個跨平台的回歸測試

```python
def test_中文以utf8儲存():
    """Windows 預設編碼是 cp950,不明確指定的話中文會壞掉。"""
    raw = path.read_bytes()
    assert "珍珠奶茶".encode("utf-8") in raw

def test_給Excel的CSV帶有BOM():
    """沒有 BOM 的話,Excel 開中文 CSV 會是亂碼。"""
    assert path.read_bytes()[:3] == b"\xef\xbb\xbf"

def test_JSON裡的中文不是轉義序列():
    """忘記 ensure_ascii=False 的話會變成 \\u73cd\\u73e0。"""
    assert "\\u" not in path.read_text(encoding="utf-8")
```

> 🔍 **這三個測試就是你的「小美保險」。**
> 你在 Mac 上開發，這三個測試會在 Windows 上幫你驗證。
> 如果接上第 13 章的 CI matrix，它們會在每次 push 時自動在三個作業系統上跑一遍。

### ⚠️ 絕對不要這樣測

```python
def test_存檔():
    save_orders(SAMPLE, "/tmp/訂單.csv")        # 🪟 Windows 沒有 /tmp
    assert Path("/tmp/訂單.csv").exists()        # 而且測完垃圾檔留著
```

用 `tempfile.TemporaryDirectory()`（標準庫）或 pytest 的 `tmp_path`。

## 14.7 🔵 最後一輪重構：檢查分層

現在功能都完成了，退一步看整個專案：

```
drinkshop/
├── menu.py       📦 只有資料          → 阿宏調價只改這裡
├── errors.py     📦 只有例外定義
├── pricing.py    🧮 純函式            → 好測
├── orders.py     🧮 純函式 + dataclass → 好測
├── report.py     🧮 純函式            → 好測
├── storage.py    💾 唯一碰硬碟的      → 用 tempfile 測
└── cli.py        🖥 唯一做互動的      → 幾乎沒邏輯，不用測
```

**自我檢查三個問題：**

1. **有沒有函式既算東西又存檔？** → 拆開
2. **有沒有函式偷看 `date.today()` 或 `random`？** → 變成參數
3. **有沒有測試需要真的建立檔案？** → 只有 `test_storage.py` 應該要

這個專案的最終數字：

| 指標 | 數字 |
| --- | --- |
| 測試數量 | 75 個 + 16 個 doctest |
| 執行時間 | 0.05 秒 |
| 需要碰硬碟的測試 | 12 個（全部用 tempfile） |
| 第三方依賴 | **0 個** |

> 🔍 **「測試跑 0.05 秒」不是炫耀，是設計品質的指標。**
> 因為 90% 的程式是純函式，所以測試不需要準備環境、不需要清理。
> 而**測試越快，你越願意跑它**；越常跑，bug 活得越短。

## 14.8 交付：讓小美也能跑

```bash
# 給小美的說明（放在 README）
git clone <repo>
cd examples

py -3 -m venv .venv          # 🪟
.venv\Scripts\activate
python -m pip install -e ".[dev]"

pytest                       # 先跑測試,確認環境沒問題
python -m drinkshop.cli demo
```

**「先跑測試」是交接的第一步。**
如果 75 個測試在她的 Windows 上全綠，你就知道環境沒問題；
如果有 3 個紅，那 3 個紅燈會直接告訴你問題在哪 —— 通常是編碼或路徑。

### 加上 CI（第 13 章）

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, macos-latest, windows-latest]
    python-version: ["3.10", "3.12"]
```

從此「在我電腦上可以跑」不再是藉口。

## 14.9 📌 這 14 章你學到的

### 語法

變數與型別 → 字串格式化 → 判斷 → 迴圈 → 資料結構 → 函式 → 模組 →
檔案 I/O → 類別 → 例外 → 標準函式庫 → 套件管理

### 但更重要的是這些

| 原則 | 第幾章 | 一句話 |
| --- | --- | --- |
| **先寫測試，需求才會清楚** | 2、3 | 寫不出 `assert` 代表你還不知道要做什麼 |
| **紅 → 綠 → 重構** | 4、7 | 沒有測試的重構叫「改東西然後祈禱」 |
| **難測試 = 設計不好** | 6、9 | 這是免費的設計警報器 |
| **把副作用推到邊界** | 8、9 | 讓 90% 的程式是純函式 |
| **把不可控的變成參數** | 12 | 時間、亂數、檔案路徑 |
| **每修一個 bug 留一個測試** | 11 | 你的測試套件會變成踩坑清單 |
| **測試名稱就是規格書** | 7 | 永遠不會過期的文件 |
| **跨平台靠 pathlib + encoding + CI** | 9、13 | 三件事解決 95% 的問題 |

## 14.10 接下來學什麼

| 方向 | 建議起點 |
| --- | --- |
| **把程式變成網站** | FastAPI（現代、型別註記友善）或 Flask（簡單） |
| **資料分析** | pandas → 但先確定你真的需要它 |
| **自動化工作** | `argparse` 做 CLI、`schedule` 排程、`requests` 打 API |
| **資料庫** | 先玩內建的 `sqlite3`，再學 SQLAlchemy |
| **程式碼品質** | `ruff`（格式化 + 檢查）、`mypy`（型別檢查） |
| **更深的測試** | `pytest` 的 fixture 與 mock、property-based testing（`hypothesis`） |
| **打包發布** | `pyproject.toml` → `python -m build` → PyPI |

### 一個建議

**找一件你每週都在手動做的事，把它自動化。**

整理下載資料夾、把發票 CSV 轉成報表、每天早上抓幾個網頁的資料……
不用大，重點是它對你有用。有用的東西你才會持續改它，才會真的學會。

而且記得：**先寫測試。**

## 🧪 最終練習

1. **加一個功能**：阿宏要「本月與上月的營收比較」。
   先寫測試（包含「上月沒有資料」的邊界），再實作。

2. **重構**：把 `daily_report` 的排版邏輯抽成 `format_table(rows)`，
   確保 75 個測試依然全綠。

3. **抓 bug**：把 `pricing.py` 的 `MEMBER_THRESHOLD` 改成 300，
   看看哪幾個測試變紅。它們是不是**剛好就是**你該改的那幾個？

4. **跨平台**：如果你有 Windows 電腦（或用 GitHub Actions），
   在上面跑一次 `pytest`。全綠嗎？沒有的話，是哪一類問題？

5. **從零再做一次**：換一個題目（記帳本、書單、健身紀錄），
   用同樣的節奏：需求清單 → 測試 → 實作 → 重構 → 分層。
