# 第 11 章：例外與除錯 —— 當事情出錯的時候

> 🎬 **情境**
> 上線第一天。客人在自助點餐機上，數量欄輸入「兩杯」。
>
> ```
> Traceback (most recent call last):
>   File "pos.py", line 42, in <module>
>     數量 = int(輸入)
> ValueError: invalid literal for int() with base 10: '兩杯'
> ```
>
> 整台點餐機掛掉，後面排了八個客人。阿宏在電話那頭很冷靜地問：「所以現在怎麼辦？」

## 11.1 😩 土法煉鋼：用 if 檢查所有可能

```python
if 輸入.isdigit():
    數量 = int(輸入)
else:
    數量 = 1

if 品項 in MENU:
    if 杯型 in MENU[品項]:
        價格 = MENU[品項][杯型]
    else:
        價格 = 0
else:
    價格 = 0

if 檔案路徑.exists():
    if 檔案路徑.is_file():
        內容 = 檔案路徑.read_text(encoding="utf-8")
```

問題：

1. **檢查不完**。檔案在你 `exists()` 之後、`read_text()` 之前被刪掉呢？
2. **主要邏輯被淹沒**。10 行程式裡 8 行在檢查。
3. **默默給錯答案**。`價格 = 0` 比直接爆炸更可怕——阿宏賠錢賠三個月才發現。

## 11.2 例外的哲學：EAFP

Python 社群有一句話：

> **EAFP — Easier to Ask Forgiveness than Permission**
> （先做再說，出事再處理，比事前檢查每個條件容易）

對比 LBYL（Look Before You Leap，先檢查再跳）：

```python
# LBYL:先檢查
if "珍珠奶茶" in MENU and "大杯" in MENU["珍珠奶茶"]:
    價格 = MENU["珍珠奶茶"]["大杯"]
else:
    處理錯誤()

# EAFP:先做,出事再說 ← Python 風格
try:
    價格 = MENU["珍珠奶茶"]["大杯"]
except KeyError:
    處理錯誤()
```

EAFP 的好處：**主要邏輯是乾淨的一行，錯誤處理集中在一個地方。**

## 11.3 💡 `try / except`

```python
try:
    數量 = int(輸入)
except ValueError:
    print("請輸入數字")
    數量 = 1
```

完整結構：

```python
try:
    危險的事()
except 特定錯誤 as 錯誤:
    處理(錯誤)
except (錯誤A, 錯誤B):        # 一次接多種
    處理()
else:
    沒出錯才做的事()           # 少用,但很精確
finally:
    一定會做的事()             # 收尾,出不出錯都執行
```

### ⚠️ 三個禁忌

**❌ 禁忌一：裸 `except`**

```python
try:
    ...
except:              # 什麼都接,包括 Ctrl+C 和記憶體不足
    pass
```

這會把 `KeyboardInterrupt`（使用者按 Ctrl+C）也接住，你的程式變成按不停的殭屍。
**至少要寫 `except Exception:`。**

**❌ 禁忌二：`except Exception: pass`**

```python
try:
    存檔(重要資料)
except Exception:
    pass                  # 資料沒存到,而且你永遠不會知道
```

這叫「吞掉例外」，是所有 debug 惡夢的源頭。
**如果真的要忽略，至少記下來：**

```python
except Exception as 錯誤:
    logging.warning("存檔失敗:%s", 錯誤)
```

**❌ 禁忌三：`try` 包太大**

```python
try:
    讀檔()
    計算()
    存檔()
    寄信()
except Exception:
    print("出錯了")      # 哪一步出錯?不知道
```

**`try` 要包「剛好可能出錯的那幾行」，不是整個函式。**

## 11.4 常見例外一覽

| 例外 | 什麼時候 | 典型原因 |
| --- | --- | --- |
| `ValueError` | 型別對但值不合法 | `int("兩杯")` |
| `TypeError` | 型別不對 | `"a" + 1` |
| `KeyError` | 字典沒這個鍵 | `MENU["綠茶"]` |
| `IndexError` | 索引超出範圍 | `清單[10]` |
| `AttributeError` | 物件沒這個屬性 | `None.strip()` |
| `FileNotFoundError` | 檔案不存在 | `open("不存在.csv")` |
| `ZeroDivisionError` | 除以零 | `總額 / 0`（空訂單！） |
| `ImportError` | 匯入失敗 | 套件沒裝 |
| `AssertionError` | `assert` 失敗 | 你的測試 |

**它們有階層關係**：

```
BaseException
 └── Exception              ← 你該接的層級
      ├── ValueError
      ├── LookupError
      │    ├── KeyError
      │    └── IndexError
      ├── OSError
      │    └── FileNotFoundError
      └── ...
 ├── KeyboardInterrupt      ← 不要接這些
 └── SystemExit
```

所以 `except LookupError:` 會同時接住 `KeyError` 和 `IndexError`。

⚠️ **`except` 的順序：從最specific 到最一般。**

```python
except Exception:        # ✖ 寫在前面的話,下面永遠不會執行
    ...
except ValueError:
    ...
```

## 11.5 `raise`：主動拋出例外

```python
def 設定數量(數量):
    if 數量 <= 0:
        raise ValueError(f"數量必須大於 0,收到 {數量}")
    ...
```

> 🔍 **什麼時候該拋、什麼時候該回傳預設值？**
>
> | 情況 | 做法 |
> | --- | --- |
> | 呼叫方給的資料就是錯的（程式 bug） | **`raise`**，讓它立刻爆 |
> | 正常業務情境的「找不到」 | 回傳 `None` 或預設值 |
>
> 例：`price_of("綠茶")` 中的綠茶不在菜單 → 這代表點餐系統讓客人點了不存在的東西，
> 是 bug，該 `raise`。
> 而 `找會員("0912...")` 查不到 → 新客人很正常，回傳 `None`。
>
> **最糟的做法是「出錯了但回傳 0」**，那會讓錯誤在系統裡默默擴散。

### 自訂例外

```python
class 庫存不足(Exception):
    """庫存不足以完成這筆訂單。"""

class 品項不存在(Exception):
    """菜單上沒有這個品項。"""
```

自訂例外的價值：**呼叫方可以精準地處理特定狀況**。

```python
try:
    下單(訂單)
except 庫存不足:
    顯示("這個品項賣完了")       # 給客人友善訊息
except 品項不存在:
    記錄bug()                   # 這是我們的問題
```

比起全部都拋 `ValueError` 然後用字串比對訊息，這乾淨太多了。

### `raise ... from`：保留原因

```python
try:
    價格 = MENU[品項][杯型]
except KeyError as 錯誤:
    raise 品項不存在(f"菜單上沒有 {品項}") from 錯誤
```

`from 錯誤` 會在 traceback 裡保留「原本是因為 KeyError」，除錯時非常有用。

## 11.6 🧪 測試例外：這是重點

**「錯誤處理」也是功能，也要測。** 而且通常是最容易被忘記測的部分。

```python
# pytest
import pytest

def test_數量為零要拋出ValueError():
    with pytest.raises(ValueError):
        設定數量(0)

def test_錯誤訊息要說明原因():
    with pytest.raises(ValueError, match="必須大於 0"):
        設定數量(0)

def test_不存在的品項拋出品項不存在():
    with pytest.raises(品項不存在):
        price_of("綠茶", "大杯")
```

```python
# unittest(標準庫)
class TestPricing(unittest.TestCase):
    def test_數量為零要拋出ValueError(self):
        with self.assertRaises(ValueError):
            設定數量(0)
```

```python
# 純 assert(Notebook 裡最方便)
def test_數量為零要拋出ValueError():
    try:
        設定數量(0)
    except ValueError:
        return                                   # 🟢 正確拋出
    raise AssertionError("應該要拋出 ValueError")   # 🔴 沒拋出就是錯
```

> ⚠️ **常見錯誤：只測成功路徑。**
>
> ```python
> def test_價格():
>     assert price_of("珍珠奶茶", "大杯") == 65     # 只測了「一切正常」
> ```
>
> 但你的程式有一半的程式碼在處理「不正常」。
> **每寫一個 `raise`，就配一個測試。** 這是很好的紀律。

### 測試清單：每個函式問自己

| 問題 | 例子 |
| --- | --- |
| 正常輸入？ | `price_of("珍珠奶茶", "大杯")` |
| 空的輸入？ | `總營收([])` |
| 邊界值？ | `結帳(199)` / `結帳(200)` |
| 型別錯誤？ | `設定數量("兩杯")` |
| 不存在的東西？ | `price_of("綠茶", "大杯")` |
| 負數 / 零？ | `設定數量(-1)` |

## 11.7 讀懂 Traceback

```
Traceback (most recent call last):
  File "pos.py", line 87, in <module>
    結帳(訂單)
  File "pos.py", line 52, in 結帳
    小計 = 計算小計(訂單)
  File "pos.py", line 31, in 計算小計
    return MENU[訂單.品項][訂單.杯型] * 訂單.數量
           ~~~~~~~~~~~~~~^^^^^^^^^^^^
KeyError: '特大杯'
```

**閱讀方法：**

1. **先看最後一行**：`KeyError: '特大杯'` ← 發生什麼事
2. **再看倒數第二段**：`line 31, in 計算小計` ← 在哪裡爆的
3. **那個 `^^^^` 標記**（Python 3.11+）直接指出是 `[訂單.杯型]` 這個存取失敗
4. **上面幾段是「怎麼走到這裡的」**：`<module>` → `結帳` → `計算小計`

> 🔍 **最常見的閱讀錯誤：從第一行開始讀。**
> 第一行只是說「這是個 traceback」，然後由外而內列出呼叫過程。
> **真正的錯誤永遠在最後一行。**

## 11.8 除錯工具

### 第 0 級：`print` 大法（誠實地說，最常用）

```python
print(f"{訂單.品項=} {訂單.杯型=} {MENU.keys()=}")
```

用第 2 章的 `{變數=}` 語法，連名字帶值一起印。

### 第 1 級：`logging`（正式程式用這個）

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
)

logging.debug("細節,開發時看")
logging.info("正常流程:訂單 %s 已建立", 訂單編號)
logging.warning("庫存只剩 %d", 剩餘)
logging.error("存檔失敗:%s", 錯誤)
```

**`logging` 比 `print` 好在哪？**

| | print | logging |
| --- | --- | --- |
| 關掉 | 要一行行刪 | 改一個 level |
| 分級 | 沒有 | DEBUG/INFO/WARNING/ERROR |
| 時間戳記 | 自己加 | 自動 |
| 輸出到檔案 | 自己寫 | 一行設定 |

⚠️ **注意寫法**：`logging.info("訂單 %s", 編號)` 而不是 f-string。
這樣在 level 不夠時，字串根本不會被組出來，省效能。

### 第 2 級：`breakpoint()`（互動式除錯）

```python
def 計算小計(訂單):
    breakpoint()          # 執行到這裡會停下來,進入互動模式
    return MENU[訂單.品項][訂單.杯型]
```

常用指令：

| 指令 | 意思 |
| --- | --- |
| `n` | 下一行（next） |
| `s` | 進入函式（step） |
| `c` | 繼續執行（continue） |
| `p 變數` | 印出變數 |
| `l` | 看現在在哪（list） |
| `q` | 離開 |

⚠️ 在 Jupyter 裡 `breakpoint()` 會開啟 ipdb 互動框，**自動化執行時會卡住**，
所以本教材的 notebook 不用它。VS Code 使用者建議直接用圖形化的中斷點。

### 第 3 級：寫一個測試重現它

**這是最有價值的除錯法。**

```python
# 阿宏回報:「有時候會員價算錯」
# 不要用 print 猜,先寫一個測試把它釘死:

def test_會員買特大杯的價格():
    assert price_of("珍珠奶茶", "特大杯", is_member=True) == 76
```

紅燈 → 修好 → 綠燈 → **而且這個 bug 永遠不會再回來**，因為測試留下來了。

> 🔍 **這叫「回歸測試」(regression test)。**
> 每修一個 bug 就留下一個測試，你的測試套件會慢慢變成一份「這個系統踩過的所有坑」的清單。
> **一年後你會非常感謝當初寫下它們的自己。**

## 11.9 🟢 把點餐機修好

```python
class 輸入錯誤(Exception):
    """使用者輸入的資料不合法。"""

def 解析數量(輸入值: str) -> int:
    """把使用者輸入轉成數量。

    >>> 解析數量("2")
    2
    >>> 解析數量(" 3 ")
    3
    """
    文字 = 輸入值.strip()
    try:
        數量 = int(文字)
    except ValueError as 錯誤:
        raise 輸入錯誤(f"數量請輸入數字,你輸入的是「{文字}」") from 錯誤

    if 數量 <= 0:
        raise 輸入錯誤(f"數量必須大於 0,你輸入的是 {數量}")
    if 數量 > 50:
        raise 輸入錯誤(f"單筆最多 50 杯,你輸入的是 {數量}")
    return 數量
```

**點餐機的主程式（互動層）負責接住錯誤，不讓它炸到客人臉上：**

```python
def 點餐機迴圈():
    while True:
        輸入值 = input("請輸入數量:")
        try:
            數量 = 解析數量(輸入值)
        except 輸入錯誤 as 錯誤:
            print(f"⚠️ {錯誤}")        # 友善訊息,繼續問
            continue
        return 數量
```

> 🔍 **注意這個分工**：
> - `解析數量()` 是**純函式**，只負責判斷和拋錯 → **超好測**
> - `點餐機迴圈()` 負責互動和顯示 → 不用測（也很難測）
>
> **把「決定」和「互動」分開**，是讓程式可測試的關鍵設計，
> 也是第 6、9 章反覆出現的同一個原則。

測試：

```python
def test_正常輸入():
    assert 解析數量("2") == 2

def test_前後空白會被忽略():
    assert 解析數量(" 3 ") == 3

def test_非數字要拋出輸入錯誤():
    with pytest.raises(輸入錯誤, match="請輸入數字"):
        解析數量("兩杯")

def test_零要被拒絕():
    with pytest.raises(輸入錯誤):
        解析數量("0")

def test_超過上限要被拒絕():
    with pytest.raises(輸入錯誤):
        解析數量("51")

def test_剛好50可以():
    assert 解析數量("50") == 50          # 邊界!
```

六個測試，涵蓋正常、空白、型別錯誤、邊界。**這才是完整的。**
