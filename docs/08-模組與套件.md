# 第 8 章：模組與套件 —— 把程式拆成好找的檔案

> 🎬 **情境**
> 你的 Notebook 已經有 87 格、400 多行。今天阿宏說「幫我改一下折扣」，你滑了三分鐘還沒找到那段程式。
>
> 更糟的是：阿宏的員工小美也想用你的計價函式，但她只能**複製貼上**你的程式碼。
> 下週你改了價格，她那份還是舊的。

---

## 8.1 😩 土法煉鋼：一個巨大的檔案

單一檔案（或單一 Notebook）到了幾百行之後：

| 問題 | 後果 |
| --- | --- |
| 找不到東西 | 每次改 code 都要先花三分鐘尋寶 |
| 無法重複使用 | 別人只能複製貼上，然後版本分岔 |
| 無法分工 | 兩個人同時改同一個檔案 = git 衝突地獄 |
| **測試很痛苦** | 要測一個函式，得先把整個 400 行跑一遍 |
| Notebook 特有 | 執行順序造成的「明明有定義卻說沒定義」 |

**Notebook 很適合「學習和探索」，但不適合「累積成果」。**
這一章教你怎麼把探索出來的東西，搬進真正的程式檔案。

## 8.2 🧪 先寫測試：這次測試決定了檔案結構

```python
# tests/test_pricing.py
from drinkshop.pricing import price_of, round_half_up      # ← 這行就是設計

def test_大杯珍奶是65元():
    assert price_of("珍珠奶茶", "大杯") == 65
```

`from drinkshop.pricing import price_of` 這一行同時宣告了三件事：

1. 會有一個叫 `drinkshop` 的**套件**（資料夾）
2. 裡面有一個叫 `pricing` 的**模組**（`pricing.py` 檔案）
3. 那個模組裡有一個叫 `price_of` 的函式

> 🔍 **測試逼你先想清楚「東西該放哪裡」。**
> 如果你寫出 `from utils import everything`，那就是在告訴自己「我還沒想清楚」。

## 8.3 模組：一個 `.py` 檔就是一個模組

```
專案/
├── pricing.py         ← 模組
└── main.py
```

```python
# pricing.py
MEMBER_RATE = 0.9

def price_of(name, size):
    ...
```

```python
# main.py
import pricing                       # 匯入整個模組
print(pricing.price_of("珍珠奶茶", "大杯"))

from pricing import price_of         # 只匯入需要的東西
print(price_of("珍珠奶茶", "大杯"))

from pricing import price_of as 查價  # 取別名
```

### 四種寫法的取捨

| 寫法 | 好處 | 壞處 |
| --- | --- | --- |
| `import pricing` | 看得出東西從哪來 | 每次都要打全名 |
| `from pricing import price_of` | 簡潔 | 多個模組有同名函式時會混淆 |
| `import pandas as pd` | 慣例別名 | — |
| `from pricing import *` | — | ❌ **絕對不要用** |

⚠️ **為什麼 `import *` 是禁忌？**
因為你不知道它到底匯入了什麼，它可能默默覆蓋掉你已經定義的東西，
而且讀程式的人完全看不出 `price_of` 是哪來的。
**唯一的例外是在互動式練習時偷懶，正式程式一律禁止。**

## 8.4 套件：一個資料夾就是一個套件

```
專案/
├── drinkshop/              ← 套件(資料夾)
│   ├── __init__.py         ← 有這個檔案,Python 就知道它是套件
│   ├── menu.py             ← 模組:菜單資料
│   ├── pricing.py          ← 模組:計價邏輯
│   └── report.py           ← 模組:報表
├── tests/
│   ├── test_pricing.py
│   └── test_report.py
└── main.py
```

```python
from drinkshop.pricing import price_of
from drinkshop import menu

print(menu.MENU)
```

### `__init__.py` 是什麼？

它是套件的「大門」，在你 `import drinkshop` 時會被執行。

- **空的也可以**，只是標示「這是套件」（Python 3.3+ 其實不放也能用，但**建議放**，行為比較明確）
- 常見用法是把常用的東西提到前面，讓使用者好用：

```python
# drinkshop/__init__.py
"""阿宏手搖飲營運工具。"""

from drinkshop.pricing import price_of
from drinkshop.menu import MENU

__all__ = ["price_of", "MENU"]     # 宣告「這個套件的公開介面」
```

這樣使用者可以寫 `from drinkshop import price_of`，不用知道它其實住在 `pricing.py`。

> 🔍 **這叫「封裝」**：你可以自由重構內部檔案結構，只要 `__init__.py` 提供的介面不變，
> 使用者的程式就不用改。

## 8.5 `if __name__ == "__main__":`

這是 Python 最常見、也最常被誤解的一行。

```python
# pricing.py
def price_of(name, size):
    return MENU[name][size]

print("測試:", price_of("珍珠奶茶", "大杯"))     # ✖ 問題來了
```

當別人 `import pricing` 時，**模組裡的所有程式碼都會被執行一次**，
所以那行 `print` 會在別人匯入時莫名其妙地印出來。

解法：

```python
if __name__ == "__main__":
    print("測試:", price_of("珍珠奶茶", "大杯"))
```

**`__name__` 是 Python 自動設定的變數：**

| 情況 | `__name__` 的值 |
| --- | --- |
| 直接執行這個檔案（`python3 pricing.py`） | `"__main__"` |
| 被別人 import | `"pricing"`（模組名） |

所以這行的意思是：**「只有當這個檔案被當成主程式直接執行時，才做底下的事。」**

用途：

- 放模組的示範／自我測試程式
- 放命令列進入點（`main()`）

```python
def main():
    """命令列進入點。"""
    ...

if __name__ == "__main__":
    main()
```

## 8.6 ⚠️ 匯入路徑：`ModuleNotFoundError` 的根源

這是初學者在「從 Notebook 搬到專案」時 100% 會遇到的錯誤。

```
ModuleNotFoundError: No module named 'drinkshop'
```

### Python 怎麼找模組？

按順序找這幾個地方（可以印出來看）：

```python
import sys
for p in sys.path:
    print(p)
```

1. 執行中的腳本所在的目錄（或互動模式的目前目錄）
2. `PYTHONPATH` 環境變數指定的目錄
3. 已安裝套件的目錄（`site-packages`）

**關鍵：是「你執行 python 的位置」在決定，不是「檔案放在哪」。**

### 三種正確解法

**✅ 解法一：從專案根目錄執行（最簡單）**

```bash
cd 專案根目錄
python3 -m drinkshop.report      # 用 -m 執行模組
pytest                           # pytest 會自動處理
```

⚠️ 注意是 `python3 -m drinkshop.report`（用點號、不加 `.py`），
不是 `python3 drinkshop/report.py`。後者會讓 Python 把 `drinkshop/` 當成根目錄，於是找不到套件。

**✅ 解法二：`pyproject.toml` + 可編輯安裝（正式做法）**

```toml
# pyproject.toml
[project]
name = "drinkshop"
version = "0.1.0"
requires-python = ">=3.10"

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"
```

```bash
pip install -e .        # -e = editable,改程式碼立刻生效,不用重裝
```

裝完之後，**在任何目錄**都能 `import drinkshop`。這是實務上的標準做法。

**✅ 解法三：Notebook 裡的臨時做法**

```python
import sys
from pathlib import Path

專案根目錄 = Path.cwd().parent          # 依你的 notebook 位置調整
if str(專案根目錄) not in sys.path:
    sys.path.insert(0, str(專案根目錄))

from drinkshop.pricing import price_of
```

⚠️ 這是**權宜之計**，不要寫進正式程式。正式程式用解法二。

### ⚠️ 絕對不要做的事

```python
sys.path.append("/Users/rex/workspace/專案")     # ✖ 寫死絕對路徑
```

換一台電腦、換一個作業系統就壞了。**寫死路徑是跨平台的頭號殺手。**

## 8.7 ⚠️ Notebook 的自動重載

在 Notebook 裡 `import` 了自己的模組，然後你去改了那個 `.py` 檔——
**Notebook 不會自動重新載入**，你會困惑「我明明改了為什麼沒效果」。

兩個解法：

```python
# 解法一:重啟 kernel(最可靠)

# 解法二:autoreload(開發時很方便)
%load_ext autoreload
%autoreload 2
```

`%autoreload 2` 會在每次執行 cell 前自動重新載入所有被修改的模組。
**這是 Notebook + 專案開發的黃金組合。**

## 8.8 標準庫與第三方模組

```python
# 標準庫:Python 自帶,不用安裝
import math, json, csv, datetime, pathlib, random, collections

# 第三方:要 pip install
import pandas, requests
```

`import` 的順序有慣例（PEP 8），由上到下分三組，中間空一行：

```python
# 1. 標準庫
import csv
from pathlib import Path

# 2. 第三方
import pandas as pd

# 3. 自己的
from drinkshop.pricing import price_of
```

⚠️ **不要把自己的檔案取名成標準庫的名字！**

```
random.py      ← 你寫的
```

然後 `import random` 會匯入**你的檔案**而不是標準庫，錯誤訊息會非常詭異。
常見受害檔名：`random.py`、`json.py`、`email.py`、`test.py`、`string.py`、`csv.py`。

## 8.9 🟢 把阿宏的程式拆成套件

```
drinkshop-tools/
├── pyproject.toml
├── drinkshop/
│   ├── __init__.py       # 公開介面
│   ├── menu.py           # 資料:MENU、SIZES
│   ├── pricing.py        # 邏輯:price_of、round_half_up
│   ├── orders.py         # 邏輯:Order、結帳
│   ├── storage.py        # I/O:讀寫 CSV
│   └── report.py         # 報表:daily_report
├── tests/
│   ├── test_pricing.py
│   ├── test_orders.py
│   └── test_report.py
└── README.md
```

**拆檔原則：**

| 原則 | 說明 |
| --- | --- |
| **按「職責」拆，不要按「型別」拆** | `pricing.py` / `orders.py` ✔；`functions.py` / `classes.py` ✖ |
| **資料和邏輯分開** | `menu.py` 只放資料，改價格不用碰邏輯 |
| **I/O 集中在一兩個模組** | `storage.py` 負責讀寫檔案，其他模組保持「純函式」→ **好測試** |
| **測試對應原始檔** | `pricing.py` ↔ `test_pricing.py`，一眼就知道去哪找 |

> 🔍 **為什麼要把 I/O 集中？**
> 因為讀寫檔案的函式很難測（要準備檔案、要清理、在不同 OS 上行為不同）。
> 把它們關在 `storage.py` 裡，其他 90% 的程式就都是純函式，**三行測試就能驗證**。
> 這個設計原則叫「**把副作用推到邊界**」，是 TDD 訓練出來的直覺。

完整的可執行版本請見 [`examples/`](../examples/)。
